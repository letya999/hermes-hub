# SPEC-0072: Automatic compaction policy and status

Draft: 2026-10-24 — pending owner acceptance. Decision: ADR-0075. Changes: CHG-0160.
Issue: #310.

- R1 (#310): A declarative `compression:` block in `spaces/<user>/settings.yaml` renders into the managed Hermes config using the same bounded key-set and fail-closed validation as `selfsettings` `compression.*`; unknown or out-of-range keys reject the whole settings load with a named error.
- R2: `auxiliary.compression` routes the summary model through the model relay (`provider: custom`, relay base URL, `${OPENAI_API_KEY}` env reference, granted logical model); with no dedicated grant it falls back to the main model route. No provider credentials enter the runtime environment.
- R3: Threshold ordering is a contract, enforced by tests: managed compressor `threshold_tokens` < hub runaway estimated-token ceiling < provider context window; the ceiling never refuses a request the compressor could still fit. Defaults unchanged: enabled, `in_place`, `micro_compact` off, `threshold_tokens` 200000.
- R4: A hub between-jobs sweep (`compression.hub_sweep.*` bounded keys: `enabled`, `threshold_tokens`, `cooldown_seconds`) compacts an over-threshold session only at a job boundary — never while a run or compact is in flight — and journals every attempt including refusals. The sweep threshold sits below the in-loop trigger: sweep is a quality knob (context-rot), in-loop is survival.
- R5: The hub compact path is a cheapest-first cascade, each stage journaled by `method`: `prune_only` (tool-output pruning commits with zero LLM calls when it fits) → `precomputed_swap` → `summary` (one call) → one shrink-and-retry → `drop_checkpoint` (explicit bounded-loss marker). No stage retries unboundedly.
- R6: Precompute speculation (`compression.hub_sweep.precompute`, bounded, default on when sweep is on): a background summary starts at ~85% of the sweep threshold; it commits only when it still describes the conversation tail and was produced for the same resolved model; at most 2 consecutive background failures per session; a late summary never blocks a user-visible turn.
- R7: A compaction journal records observed events only: `{trigger(auto_inloop|auto_sweep|manual|overflow), engine(hub|native|provider), method, tokens_before_est, tokens_after_est, failure_class, at}`. `context_status` and `/usage` report observed counts, last event, effective threshold and its provenance (`declared|default`), plus current estimate with provenance (`measured|estimated`); unavailable measurements serialize as `null`, never fabricated.
- R8: Opt-ins stay off by default: `micro_compact`, idle compaction, provider-native compaction (`engine: provider`), `context.engine`/pluggable engines.
- R9: Effective policy is inspectable via `settings_get` and overridable via `settings_set` with the existing bounded overlay and scheduled restart; per-space declarative values and runtime overrides compose predictably (settings first, overlay on top).
- R10: Summary-backend overload or failure preserves the transcript and surfaces a named `failure_class`; it is journaled and visible in `context_status`.
- R11: After any commit the next turn carries a bounded post-compact notice re-stating durable hub state (active goal, pending items); the notice is generated by the hub, counted in the journal, and never contains transcript or summary text.

Acceptance A1..A11: each requirement has regression tests through its real Go boundary (settings parse/validate, render output, journal write, status read, sweep decision, cascade stage selection, precompute boundedness, refusal paths); render defaults unchanged byte-for-byte. Docker + real-provider acceptance is separate evidence and cannot be asserted from fixtures.
