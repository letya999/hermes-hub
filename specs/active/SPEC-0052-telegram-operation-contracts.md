# SPEC-0052: Telegram operation reliability amendment

Frozen: 2026-10-13, after the owner's explicit implementation instruction. Supplements SPEC-0015,
SPEC-0037, SPEC-0047/0048, SPEC-0050 and SPEC-0051 without rewriting their history.
Design: [ADR-0035](../../docs/adr/ADR-0035-telegram-operation-contracts.md).
Traceability: [CHG-0091 verification](../../.work/in-progress/CHG-0091-telegram-operation-contracts/verification-plan.md).

## R1: Image input

1. Supported image bytes (PNG/JPEG/WebP) remain inspectable without a filename
   extension and with a misleading filename or channel MIME. The actual decoded
   format determines the provider MIME. Unsupported/corrupt input is rejected.
2. Confined regular-file reads, aggregate byte bounds, dimensions, pixel bounds,
   1-8 image count, order and per-path authorization remain enforced. An invalid
   member prevents sending any member to the provider. No CLI rename is required.
3. Telegram photos without names receive a stable safe synthetic name containing
   the staged ID and supported detected suffix; original document names remain
   available as metadata. Replayed intake does not overwrite a consumed receipt.
4. Single inspection and image-edit input share format validation. Generation
   credentials and output-format selection remain separate contracts.

## R2: MCP environment and availability

1. The owning direct MCP child explicitly receives model credential and selected
   config locator, in addition to the SPEC-0051 control/identity/policy variables.
   Unrelated provider keys are absent. Values are never embedded in tool results,
   checked-in YAML, diagnostics or CI artifacts.
2. Missing or unresolved required references produce a specific configuration
   error; a literal placeholder is not treated as a usable credential/URL.
   Optional inactive integrations do not become mandatory startup dependencies.
3. A synthetic real-loader test resolves rendered/materialized config using pinned
   Hermes, launches the child and observes routine and image calls at local fixtures.
   Raw SDK env tests and `/models` presence do not prove this requirement.
4. Native Hermes vision stays disabled. Authorization is enforced by current
   ToolHub selections and scoped roots, not by tool descriptions or annotations.

## R3: Watcher discovery and behavior

1. Direct MCP and projected ToolHub metadata describe the same supported modes.
   Watcher creation requires URL, optional first-capture regex, timezone, schedule
   and notification text; old/new previews are supported, not static-text-only.
2. Baseline success is silent; unchanged value is silent; a changed value produces
   one logical notification containing old/new bounded previews. Fetch/regex errors
   preserve baseline and settle as failure. Ticks never invoke a runtime/model.
3. Surrounding URL whitespace may be trimmed. Embedded control/format characters,
   invalid URLs and credential-bearing URLs are rejected explicitly, not rewritten.
   Existing private-IP, redirect, body-size and timeout protections remain.
4. Agent refusal is correct only when the actual selected surface/grant, source or
   validated arguments are unavailable. Record that reason separately from a
   successful tool call; never infer readiness from the answer text alone.

## R4: Relative reminder creation and replay

1. Creation with `kind=reminder` accepts `after:<Go duration>`. Proposed bounds:
   1 second through 365*24 hours, integral seconds; zero/negative/fractional/overflow
   and unsupported units fail validation. `once:` and cron retain their contracts.
   `after:` on other kinds or on update is rejected; moving an existing reminder
   uses an explicit absolute update. No new recurring-relative mode is introduced.
2. At first accepted creation, sample one trusted server clock T; resolve deadline
   T+delay and persist canonical `once:<UTC>` before scheduler dispatch. Validation
   and creation share that sample. Response exposes receipt time, requested rule,
   resolved deadline and current status. The bot displays that returned deadline.
3. A creation receipt persists the original requested expression, resolved deadline
   and canonical intent digest. Digest covers owner/context, audience/task/topic,
   ID, kind, input, timezone, probe/expect/source selections and creation options;
   excludes mutable runtime status and timestamps generated by the server.
4. Under the writer lock: exact same-owner ID+intent replays the receipt; changed
   intent returns conflict (HTTP 409); foreign-owner collisions reveal no receipt.
   Check replay before future-deadline validation so a completed retry is observable.
   Two concurrent exact creates have one atomic commit and the same deadline.
5. New tombstones preserve creation receipt and indicate deletion; exact replay
   observes retired status without reactivation. Legacy records lacking receipts
   are never guessed to match; their duplicate/retired IDs remain conflicts.
6. Restart retains the deadline. Before the deadline there is no delivery; firing
   creates one logical occurrence/delivery and no agent/model work. Existing overdue
   and uncertain transport policy stays explicit; physical exactly-once is not claimed.
7. A new ID is a new intent, even for equal text. An agent must observe the original
   ID after uncertain create and must disclose an already sent reminder rather than
   silently creating a replacement. Universal model-intent deduplication is outside
   this contract and must not be advertised as implemented.

## R5: Approval send, decision and cleanup

1. A queued approval is actionable only for its current request ID, matching
   principal/context/conversation/audience/run generation, unexpired pending state,
   no cancellation and no saved decision. Recheck immediately before Telegram send.
   New approval receipts retain immutable run/generation provenance. Legacy queued
   records lacking it must be reconciled against the original native request before
   rendering; missing provenance cannot authorize an actionable message.
2. Superseded A while B is pending, decided A while the run continues, expired
   requests and terminal runs never produce a new actionable A keyboard. Corrupt
   or unreadable mappings are quarantined/retryable errors, not silent success.
3. Durable intent acknowledgement means saved, not resumed/completed. Pending or
   uncertain decisions are not presented as applied; reconciliation observes the
   original native run and never executes a new generation or blanket approval.
4. Message cleanup is limited to verified sent-message receipts. Keep the receipt
   on API/persistence failure. Successful keyboard sends are not resent merely
   because local receipt persistence failed; use saved send progress or explicit
   uncertain handling. Repeated cleanup has no foreign-message effects.
5. Existing conflicting-choice, sender, policy, generation, expiry and protected
   write checks stay enforced. Read-only listing cannot inherit an old write intent.

## R6: Exact outbound files

1. Auto-delivery remains restricted to newly produced direct files in the existing
   documents/images/videos buckets and allowed root ZIPs. Other files require an
   explicit `MEDIA:` marker; marker processing does not broaden source authorization.
2. Instructions on both surfaces name these limits. Requesting existing files
   delivers exact bytes, not a regenerated paraphrase or inline contents by default.
   Original files remain unchanged. Existing bounded endpoint/spool progress applies.
3. Two-file acceptance checks independently read sent bytes and compare hashes with
   synthetic originals. Failed fetch/send has visible failure/uncertain state and
   cannot be represented as delivered by path text or an assistant assertion.

## R7: Subsequent album slice

1. Core R1-R6 acceptance is independent of album aggregation. Implement R7 only
   after it has its own red regression and ownership/recovery review.
2. Album key includes principal/context/conversation/chat/topic and media_group_id;
   dedupe by message/update ID. Persist staged members before acknowledging intake.
   Proposed quiet window is 2 seconds, hard collection window 10 seconds; these are
   bounded heuristics, not Telegram completeness guarantees. Sort by message ID.
3. Maximum eight images and the existing shared inspection byte cap. Over-limit or
   incomplete/failed intake reports an error and never sends a silently truncated
   set to the provider. Late members produce an explicit late-member outcome; no
   automatic replay of the already admitted album job.
4. Group admission carries trusted `InboundIDs` (maximum eight), preserves old
   singular `InboundID`, and rejects conflicting forms. Each member is fetched with
   its owner's authorization before one job starts. Restart during collection or
   admission does not duplicate jobs or mix groups; receipts survive reconciliation.
5. Explicitly comparing two individually uploaded workspace files remains supported
   without an album collector. No arbitrary memory/state paths are auto-attached.

## Completion evidence

Contract/regression, real pinned-Hermes Docker and actual Telegram/model evidence
are separate results. `just check` must pass with >=85% own Go statement coverage;
image-side code changes require the appropriate Docker gate. Missing grants/models
are BLOCKED, never fixture-promoted PASS. New catalog versions are published and
selected explicitly without silent rights expansion. External sending/publication
requires its actual instruction; design work alone does not authorize it.
