# ADR-0007: consumer_id — дискриминатор нескольких кредов на connection

## Контекст

Enrollment разрешал ровно один active credential на пару `(context, connection)`. Это корректно для
«один сервис — один кред», но ломает реальный случай: одна capability держит несколько ключей для
разных целей — несколько SSH-ключей под разные host alias, отдельные токены под разные MCP/CLI.
Обходные пути (новый `connection_id` на каждый ключ) заставляли выдумывать фиктивные connection.

## Варианты

- Оставить инвариант и плодить connection IDs на каждый ключ — теряется пространство имён и смысл connection.
- Список кредов внутри одного credential — ломает revision/rotation/lease модель.
- Отдельный необязательный `consumer_id` на request/credential, расширяющий кортеж уникальности —
  выбрано.

## Решение

`CreateRequest.ConsumerID` — необязательный canonical ID (`[a-z][a-z0-9_-]{0,39}`), обозначающий
потребителя креда (`mcp-github`, `cli-git`, `ssh-box`). Уникальность active credential и pending
request считается по `(context, connection, consumer)`; пустой consumer дедупится только с пустым.
Поле протекает в `Request`, `Credential`, ledger events и сохраняется при rotation — ротация с
другим consumer отклоняется. Старые клиенты без поля получают прежнее поведение.

## Последствия

Затраты: новое поле в трёх DTO и событиях, дедуп-логика и тесты. Ограничения: consumer не является
authorization — grants/bindings остаются единственной границей доступа. Миграция не нужна: существующие
credentials имеют пустой consumer и конфликтуют только между собой, как раньше.

## Когда пересматривать

Если появится иерархия потребителей (орг/команда/tool) или потребуется переиспользование одного
креда несколькими именованными потребителями без grants.
