# План приёмки M10 A–C после стабилизации

## История разрешения и изоляция

После первоначального указания владельца 2026-10-11 Docker-проверки были
остановлены. До последующего явного разрешения сборки, инспекция и очистка
не выполнялись. Фактические результаты записываются в state.yaml; сам список
проверок ниже не является заявлением об их успешном выполнении.
Код находится в hermes-hub-m10a, ветка feat/m10-phase-a; публикация не выполнялась.

Позже в тот же день владелец явно разрешил локальные Docker-проверки. Ограничение
снято для тестов: используется общий разрешённый daemon, отдельный тег
hermes-hub:m10a-verify и временные fixtures. Основной стек не изменяется. Отдельный daemon больше не является условием
локальной приёмки после этого явного разрешения владельца.

## 1. Проверки без Docker

- `just check`: все тесты, race detector, перемешанный порядок, общее покрытие
  собственного Go-кода не ниже 85%, gofmt, go vet, staticcheck, ссылки документации
  и actionlint. На этой Windows-машине для race используется установленный GNU
  gcc: `CC=C:/msys64/ucrt64/bin/gcc.exe` и его каталог первым в PATH.
- `just security`: отсутствие достижимых Go-уязвимостей и high/critical npm-рисков.
- Проверка новых границ: исходный файл остаётся после отправки; архив не заменяет
  существующие данные; каждый путь в массиве авторизован; ссылка не расширяет
  разрешённую папку; повреждённая квитанция не приводит к падению или повторному
  исполнению; второй писатель не меняет spool.
- Проверка восстановления и прав: отменённые и устаревшие задачи не исполняются и
  не доставляются; результат восстанавливается без повторного fetch/script;
  digest не теряет неотправленные изменения и не застревает на старых ошибках;
  knowledge не раскрывает соседний контекст; usage не придумывает измерения.
- Статический анализ и проверка секретов: новые находки отдельно от существующих
  проблем; учебные строки в тестах не считаются настоящими ключами без проверки.
  Установленный gosec не читает export data Go 1.27 (version 5). Дополнительный
  анализ выполнен upstream-версией v2.29.1-0.20261009120814-7b1b5cebe007 через
  go run, без замены системного инструмента: ошибок загрузки пакетов нет.
  Имеющиеся G304 на внутренних именах квитанций и явных CLI-путях рассмотрены;
  совпадение правила не означает доказанную уязвимость. Общий старый SAST backlog
  не объявляется устранённым. TruffleHog wrapper не поддержал worktree .git-file;
  Ruff wrapper также вернул ошибку. Их исправление и повторный запуск — отдельные
  незакрытые проверки; gitleaks изменённых файлов прошёл.

## 2. Локальная проверка Docker после разрешения владельца

Использовать отдельные теги hermes-hub:m10a-verify и
hermes-hub:m10a-verify-control, временные тестовые профили и синтетические
провайдерские ответы. Рабочие контейнеры, данные и основные теги сохраняются.
Обычный just docker-check использует общие фиксированные test/test-control:
на общем daemon его этапы выполняются отдельно штатным devcheck с указанными
тестовыми тегами. Это тот же набор проверок, но без перезаписи общих тегов.

Сборка через `go run ./cmd/devcheck docker-build hermes-hub:m10a-verify prod`
и соответствующий prod-control сохраняет принудительный BuildKit.
Последовательно проверить:

1. Контрольный образ и smoke runtime, без настоящих провайдерских аккаунтов.
   Файловые symlink/ZIP/scope-регрессии дополнительно выполняются под Linux,
   поскольку Windows может пропустить symlink-кейс при отсутствии прав.
2. Контракты pinned Hermes: холодный старт, поток, approvals, crash/resume без
   повторного ввода, idle при активных leases, пробуждение due routine и финал.
3. Контракты инструментов и границ capability.
4. Managed network/supervisor и scratch canaries, включая quarantine paused exec.
5. Адресную очистку ресурсов с подтверждённым владением и лимит BuildKit cache
   8 GB. Общий docker-clean на этом shared daemon не используется: он перечисляет
   старые пустые сети и теги других проверок; имя ресурса само по себе не доказывает
   владение текущего прогона. Рабочие и неидентифицированные ресурсы сохраняются.

Команды остальных этапов для повторения (PowerShell, последовательно):

```powershell
go run ./cmd/devcheck docker-build hermes-hub:m10a-verify-control prod-control
docker run --rm --entrypoint docker hermes-hub:m10a-verify-control --version
go run ./cmd/devcheck docker-smoke hermes-hub:m10a-verify
go run -tags integration ./cmd/devcheck hermes-contract hermes-hub:m10a-verify
go run -tags integration ./cmd/devcheck hermes-capability-contract hermes-hub:m10a-verify
go run -tags integration ./cmd/devcheck managed-network-canary hermes-hub:m10a-verify
go run -tags integration ./cmd/devcheck managed-supervisor-canary hermes-hub:m10a-verify
go run -tags integration ./cmd/devcheck scratch-workload-canary hermes-hub:m10a-verify
$env:HUB_SCRATCH_FAULT_IMAGE='hermes-hub:m10a-verify'
go test -tags integration -run TestDockerScratchExecPausedQuarantine ./internal/toolhub
```

При первой ошибке остановить приёмку, сохранить stage, длительность, fixture ID
и диагностические события. Не повышать timeout или ослаблять проверку владения
просто ради зелёного результата. Подтверждённое несоответствие исправляется
в тесте: supervisor допускает четыре минуты readiness, поэтому холодный старт
имеет пять минут вместе с исполнением; тёплая работа и проверки прав не ослаблены. Предыдущий полный прогон завершился timeout
на due routine wake; повторный был остановлен владельцем. Причина предыдущего timeout непосредственно не измерена. В разрешённом итоговом
прогоне due wake прошёл; найден и исправлен более короткий, чем production
readiness, бюджет ожидания теста. В другом прогоне зарегистрированный run вернул
uncertain: fixture теперь наблюдает тот же RunID через production resume с пустым
вводом. Потеря исходной записи, смена run или отсутствие завершения за ограниченное
время остаются ошибкой. Повторный полный прогон после этих исправлений успешно завершён; точные
результаты и ограничения сохранены в state.yaml.

После сборки итогового образа выполнить на том же разрешённом локальном daemon:

`HUB_SCRIPT_IMAGE=hermes-hub:m10a-verify go test -tags integration -run TestDockerM10ScriptMemoryIsolation -v ./internal/supervisor`

Ожидания: обычный emit успешен; превышение памяти отмечено Docker как OOMKilled;
нет сети, mounts, секретов и привилегий; временные контейнеры удалены; следующий
обычный скрипт работает. Ранее этот тест прошёл на промежуточном образе, что не
заменяет итоговую приёмку всех изменений.

## 3. Сквозные сценарии на тестовом профиле

- Файлы (#150/#151): два изображения в одном запросе; архив с одинаковыми именами
  в разных передачах; traversal, symlink и zip bomb; сбой до/после квитанции;
  повторная доставка и ACK; оригиналы остаются целыми.
- Telegram (#194): команды status/routines/connectors/usage не вызывают модель;
  approval доступен только своей аудитории, повторный callback не повторяет
  действие; ответы приходят в нужную forum/direct-message topic.
- Usage/idle (#195/#214): два задания одной сессии дают дельту; смена/сброс/отсутствие
  счётчиков отмечены честно; фоновый учёт не будит runtime; активная работа не
  прерывается, idle отсчитывается после освобождения последнего lease.
- Routines (#247/#248/#250/#251): reminder без LLM; script ограничен; private-IP,
  redirect и credential URL отвергнуты; GitHub сравнивается по state; отсутствие
  regex capture сохраняет baseline; snooze/delete/revoke блокируют старую работу;
  digest включает только свои выбранные источники и догоняет остаток изменений.
- Knowledge (#249): только GET и свои контексты, provenance соответствует файлу;
  превышение размеров и отозванный токен отвергнуты; текст не меняет полномочия.
- Phase C: mock проходит настоящий queue pipeline и сохраняет свои attachments;
  одинаковый client ID разных владельцев независим; apply сначала валидирует весь
  файл, не удаляет отсутствующие ресурсы, требует явную маршрутизацию и не принимает
  offline check; сборки выполняются штатным путём с BuildKit.
- Research (#181): сверить закреплённый commit ai-stp и таблицу поддерживаемых
  компонентов; никакую совместимость Hermes/ai-stp не заявлять по одной заметке.

Проверки реального Telegram требуют отдельного разрешения владельца на отправку
в специально выбранный тестовый чат. Mock и локальный HTTP fixture этого не доказывают.
Никакие настоящие токены, transcripts или персональные данные не сохранять в Git.

## 4. Условия закрытия

Все проверки без Docker успешны; локальные Docker gates успешны на итоговом
коде; timeout due routine wake объяснён и устранён либо доказан как ограничение
проверочного окружения; реальные каналы имеют отдельные результаты приёмки.
Записать версии/ревизию, даты, команды, результаты и ограничения в state.yaml.
Локальная реализация и приёмка завершены. Настоящие Telegram/provider аккаунты
не проверены; этот внешний этап отдельно отмечен в state.yaml и не объявляется
успешным. Commit/push/публикация — отдельное действие.
